# MaixCAM 钢球 AI 追踪

## 当前生产路径

当前比赛与日常测试只使用 MaixHub 模型追踪。Windows 上位机不再提供
传统视觉 V1/V2 的切换或调参入口；后续迭代集中在模型版本、统一置信度阈值、
IoU、目标点和短时续跟帧数。

板端启动时会读取
`/root/pipe_ball_vision/runtime/ai_runtime_config.json`。在上位机点击
**应用 AI 配置**且收到设备 ACK 后，配置立即生效并持久化；下次部署或重启
仍使用同一组模型与阈值。模型热切换会先验证并加载候选模型，失败时继续使用
原模型，不会把控制链路切到无模型状态。

下文中的传统颜色/几何识别说明保留为历史实现记录和源码维护参考，不再是
Windows 上位机的可选运行方案。

这里只保留本次“车载平衡滚球运动控制系统”需要的视觉代码：

```text
MaixCAM 取图
  -> 右端小区域拟合进入窗口的长绿色轨道段
  -> 固定左胶布 + 更新右端 X/Y，得到动态轴线
  -> MaixHub 模型识别钢球
  -> 将钢球投影到动态轴线并做轻量时间滤波
  ├-> UART 50 Hz 发送给 STM32
  └-> RTSP 图传 + UDP 遥测发送给 Windows
```

入口是 `maixcam/main.py`，参数集中在 `maixcam/ball_config.py`。

## 运行模式

| `APP_MODE` | 用途 |
|---|---|
| `"stream"` | 默认比赛模式：识别、STM32 UART、RTSP图传和 Windows遥测 |
| `"track"` | 纯识别性能基线，不启用 RTSP |
| `"record"` | 无电脑/断网时的 MaixCAM本地录像兜底 |
| `"serve"` | 临时只读下载板端测试文件 |

模式入口彼此隔离，不把录像和网络调试逻辑塞进识别核心。

## 当前车载标定

当前参数根据 2026-07-31 车载录像重新核对：

- 左端胶布在相机坐标中固定，检测坐标端点为 `(26,99)`；右端会同时左右、
  上下移动，因此在右侧局部区域内测量二维端点。直接阈值找黑胶布会与后方
  黑色电机和线缆连成一块，因此仍以绿色轨道为测量对象。
- 候选必须是从搜索框左侧进入的长绿色段；其最小外接矩形右端就是轨道右端
  `(x,y)`。当前按两张极限姿态将色块末端沿轨道内缩约 `14 px` 对齐黑胶布
  基准；二维端点还必须落在已知机械行程内，孤立反光不会参与建轨。
- 右端每 4 个相机帧更新一次，对 X/Y 使用同一层轻量平滑。未检测到候选时
  保持最近端点，不再突然跳回固定长度。
- 原来的两端螺丝已拆除，螺丝排除区、端点圆检测和圆心向内偏移均已关闭。
  黑胶布自身位于物理端点范围外，不会作为钢球建轨。
- 钢球始终由当前 MaixHub 模型识别；管道小区域扫描只更新坐标参考，不会
  切回传统钢球检测。
- 检测通道为 `480×360 @ 60 FPS`。Windows 图传保持 `448×336、
  1 Mbps`，编码 20 FPS；Windows 界面本来就只渲染 20 FPS，因此不降低
  预览分辨率，同时减少编码与控制通道的资源争用。
- 保留自动曝光；当前照明下 2 ms 手动曝光实测过暗，不能使用。

如果相机、左胶布或右端结构发生机械变化，必须先重标
`AXIS_START`、`AXIS_END`、`PIPE_ANCHOR_SEARCH_ROI` 和右端二维行程，
不能用放宽钢球门限掩盖机械坐标变化。

### 钢球 0% / 100% 行程标定

绿线描述管道几何，控制百分比描述钢球中心能够实际滚动的机械行程，两者分开
标定。Windows 控制台的 **AI 参数 → 钢球机械行程标定** 提供两个按钮：

1. 将钢球静止放到左侧机械极限，等待状态显示“稳定”，点击
   **当前位置设为 0%**。
2. 将钢球静止放到右侧机械极限，等待状态显示“稳定”，点击
   **当前位置设为 100%**。

控制台采用最近 1.2 秒内最多 24 帧真实测量的中位数，波动超过 `2.5 px`
时拒绝标定。得到的 `travel_start_px`、`travel_end_px` 写入板端运行配置，
重启和重新部署后仍保留。以后更换钢球、端部挡块或胶布时重复这两个步骤，
不修改管道识别源码。

### 640×480 视野模式

实机 GC4653 同时输出 1280×720 和 640×480 对比确认：

- 传感器工作在 1280×720、60 FPS 的 16:9 模式。
- 640×480 输出保留基本相同的垂直视野，并中心裁掉左右视野后缩放为 4:3。
- 当前 24.7 cm 管道能够完整进入 4:3 画面，因此中心裁切提高了管道方向上的像素密度。
- 需要更大安装余量时可改用 640×360，但需要重新标定 ROI 和管道轴线。

可单独运行 `maixcam/fov_probe.py`，在同一传感器会话中交替查看
1280×720 和 640×480 视野。诊断结束后重新运行项目入口 `main.py`。

### 分阶段验收，不再用一个总百分比调参

每轮只改变一个条件，并用 `iteration_client.py mark` 标记阶段：

1. 空管 20～30 秒：必须 `measured=0`，用于约束反光和背景误报。
2. 钢球分别静止在左、中、右三个非端点位置，各 10 秒：逐帧对照录像，
   暂定目标为真实测量率不低于 99%，且测量点始终落在球体内。
3. 慢速左右滚动 20 秒：暂定真实测量率不低于 95%，最长连续丢测不超过
   3 个识别帧。
4. 快速滚动和换向 20 秒：先记录球速分组和最长丢测，再决定是否调整
   `max_frame_jump_px`、局部窗口或预测参数，不能同时改 LAB阈值。
5. 球靠近左右实体端点：验证真球可从 2%～98% 建轨、已确认后仍可跟到
   约 1.5%～98.5%，同时空管
   管口反光仍不能新建轨迹。
6. 只移动、抬高和转动管道：重点看 `pipe_valid`、`pipe_age_frames` 和动态
   轴线叠加，不把管道坐标错误归咎于钢球检测。
7. 最后才做手部遮挡和上车震动；遮挡阶段单独统计预测续航，不能混进
   有球可见阶段的“准确率”。

一轮只依据对应阶段的录像真值和拒绝原因改一类参数，修改后必须重新跑
空管负样本，防止召回率提高的同时重新引入假锁定。

## 日志字段

程序每 0.5 秒输出一个统计窗口：

```text
fps=55.0 measured=100.0% valid=100.0% coast=0
raw=2 cand=1 detect_ms=4.9 error=-23 velocity=18
```

- `measured`：这一窗口中真正检测到钢球的帧比例。
- `valid`：包含短时预测续航在内，可供控制器使用的帧比例。
- `coast`：因短时遮挡而使用预测值的帧数。
- `raw/cand`：原始色块数/通过几何筛选的候选数。
- `detect_ms`：单帧检测平均耗时。
- `error`：钢球相对目标点的轴向像素误差。
- `velocity`：估计轴向速度，单位为像素/秒。

## 无界面部署与比赛上位机

日常迭代不再要求通过 MaixVision 点“运行项目”。第一次安装依赖后，推荐
双击一体化上位机：

```text
Vision/windows/start_operator_console.cmd
```

浏览器中的本地控制台同时显示实时标注画面、识别指标、当前模型、统一置信度
阈值、实验阶段、设备日志和部署版本；可直接热切换已安装的 MaixHub 模型、
部署重启、开始/结束录像和截图。控制台与 Codex
共用 `127.0.0.1:8770` 的 JSON/画面接口，不需要自动操作浏览器。它背后仍会
检查全部板端 Python 源码，按内容哈希通过 SSH/SFTP 上传成可回退版本。
波形区提供 13 组实时信号：6 组视觉输出和 7 组 STM32 控制反馈。点击
“波形”可逐项勾选，也可用“常用 / 视觉 / 控制 / 全部”快速切换；选择会
保存在本机浏览器。默认只显示视觉位置、控制位置与误差、PID 和实际电机
命令，避免同时绘制过多曲线影响观察。
结构化 API、命令行、日志、定时实验与回退说明见
[`VISION_AGENT.md`](VISION_AGENT.md)。

MaixVision 只保留为查看传感器、固件升级和临时单文件探针的备用工具，不再
是算法迭代闭环的必需环节。

## 比赛图传、Windows录像与在线调参

默认配置已经是 `APP_MODE = "stream"`。

准备一次 Windows环境：

```powershell
python -m pip install -r Vision\windows\requirements.txt
ffmpeg -version
```

`ffmpeg` 必须已加入 `PATH`。不要关闭 Windows防火墙；如果系统首次询问
是否允许 Python接收局域网 UDP，只允许当前比赛使用的专用/私有网络。
启动器使用 `python.exe`；不要自行改成 `pythonw.exe`，Windows防火墙会把
二者视为不同程序，可能出现“有图像但没有 UDP标注”的现象。

推荐运行：

1. 双击 `Vision/windows/start_operator_console.cmd`。
2. 页面打开后点击“部署并重启”完成首次部署，或在板端已经运行时等待
   自动连接预览。

如果板端已经由 `vision_agent.py start` 启动，也可只启动接收端：

```powershell
python Vision\windows\stream_receiver.py
```

USB网卡默认寻找 `10.16.6.1`。Wi-Fi地址不同时：

```powershell
python Vision\windows\stream_receiver.py --device-ip 192.168.1.50
```

窗口操作：

- `Q`/`Esc`：正常结束并封装录像。
- `S`：保存带当前叠加层的截图。
- 浏览器控制台的 **AI CONTROL** 面板只显示已安装模型、统一置信度阈值、
  IoU、目标位置和短时续跟帧数；5%、13%、20%、30% 可一键预选。
- 波形选择器可显示视觉位置、速度、误差、AI 置信度、识别 FPS、链路耗时，
  以及 STM32 控制位置/误差、速度、PID、电机命令、视觉帧龄、反馈丢失和
  HAL 电机状态。
- 调整后点击**应用 AI 配置**；只有显示“设备已确认应用”才算生效并持久化。
- 红色圆圈表示当帧真实检测点；黄色菱形表示发给控制链路使用的滤波/预测
  位置；紫色十字是目标停球点。
- 完整相机画面不会被文字覆盖；状态信息位于画面下方独立区域。
  `delay` 是视频链路延迟，`sync` 是匹配到的 UDP数据与视频时间差。
  正常无需修改“时间微调”。

每次 Windows实验保存在：

```text
Vision/captures/stream_sessions/stream_YYYYMMDD_HHMMSS/
  video.mp4          # Windows H.264 录像（当前源为 20 FPS）
  tracking.csv       # 设备识别时间轴的结构化遥测
  stm32_feedback.csv # STM32 PID、实际电机命令、视觉帧龄与 HAL状态
  telemetry.jsonl    # status/tracking/stm32_feedback/ACK 原始报文
  video_frames.csv   # 解码帧时间戳、匹配遥测、延迟和主动丢帧
  events.jsonl       # 订阅、调参、实验标记和异常事件
  session.json       # 本次地址、参数、数量和结束状态
  analysis.txt       # 退出时自动生成的可读复盘
  analysis.json      # 同一份复盘的机器可读入口
  ffmpeg.log
```

Windows只建立一条 RTSP连接；FFmpeg解码同一数据流用于低延迟预览，同时
把 MaixCAM 已编码的 H.264 直接保存到临时 MKV，正常退出时再无损封装为
MP4。录像分支不再二次运行 x264 编码，降低电脑 CPU 占用并保留板端原始
画质。显示框线不烧入原始录像。接收线程持续读取视频并只把最新帧交给
界面，因此调参、拖动窗口或短时卡顿不会形成积压。叠加层不使用“最新
UDP包”，而是根据每张视频帧的输入墙钟时间，在历史遥测队列中选择同一
时刻的数据。`ffmpeg.log` 仍保留启动、异常和每秒一个时间戳样本，不再
重复写入每帧两行的 `showinfo` 信息。

录像后统计：

```powershell
python Vision\tools\analyze_tracking_log.py `
  Vision\captures\stream_sessions\<本次目录>\tracking.csv
```

程序会联合 `video.mp4` 与 `video_frames.csv`，报告录像参数、视频映射窗口、
UDP日志频率、设备识别 FPS、检测耗时、视频延迟、视频/遥测匹配误差、
主动丢帧数、接收间隔和运动速度分组。正常退出时已经自动生成报告，无需
再手动运行分析命令。没有有效轨迹时速度未知，分析器会单列为 `untracked`，
不会再误归到“慢速”。未标记整段的 `measured/valid` 表示系统可用率，
不是带真值的识别准确率；比较参数效果应以 `mark` 划定的实验阶段为准。

STM32控制反馈可离线生成 SVG，无需安装额外绘图库：

```powershell
python Vision\tools\plot_stm32_feedback.py `
  Vision\captures\stream_sessions\<本次目录>
```

输出为同目录的 `stm32_feedback.svg`，包含参考位置/目标/控制误差、速度、
乘 `motor_direction` 前的 P/I/D、实际有符号电机命令和视觉数据年龄。
橙色虚线表示 STM32反馈 `seq` 跳号，红色点线表示
`motor_status != HAL_OK`。脚本也可直接读取 `stm32_feedback.csv` 或
`telemetry.jsonl`。

### 让 Codex/脚本接入整轮实验

监控运行时只在本机 `127.0.0.1:8765` 开放迭代接口。内存状态约每
0.1 秒更新，供接口实时读取；磁盘状态文件最多每 0.5 秒原子更新一次，
避免高频小文件写入：

```text
Vision/runtime/live_status.json
```

它包含当前会话目录、视频延迟、同步误差、识别状态、参数和最近一条命令
结果。启动阶段还会明确显示 `discovering_telemetry`、
`connecting_video` 或 `waiting_for_first_frame`，便于区分 UDP、RTSP 和
首帧问题。即使设备尚未传来首帧，`stop` 也会立即打断等待并正常保存
`status=stopped`，不必等完整发现超时。这样监控窗口保持运行时，
Codex可以直接参与实验：

```powershell
# 实时状态；实验结束后自动退回读取最后状态文件
python Vision\windows\iteration_client.py status

# 标记接下来这一段动作，写入 events.jsonl
python Vision\windows\iteration_client.py mark "慢速左到右"

# 保存当前叠加画面
python Vision\windows\iteration_client.py snapshot

# 中文别名或协议字段均可，设备 ACK 后 status 才显示 applied
python Vision\windows\iteration_client.py set "目标位置=0.50" "续航帧数=3"

# 两帧确认建轨，已确认轨迹用几何与连续性续跟
python Vision\windows\iteration_client.py set "重找可信度=60" "跟踪可信度=20" "首次找球端部禁区=0.02"

# 仅在自动同步后仍有固定错位时使用，单位 ms
python Vision\windows\iteration_client.py sync 20

# 安全结束、封装录像并自动分析
python Vision\windows\iteration_client.py stop
python Vision\windows\iteration_client.py report
```

“端点容差”是旧的标定外延参数；“首次找球端部禁区”和“跟踪端部禁区”
才是当前物理排除区。它们可以热调，但每次放宽后必须重跑空管负样本。
接口只能调整协议白名单内的视觉参数，不包含电机使能、运动或 PID命令。
以后推荐每轮依次标记“静止、慢滚、快滚、换向、遮挡”，结束后 Codex直接
读取 `analysis.json`、录像和标记区间做复盘，再通过同一接口下发下一组视觉
参数。自动报告会按相邻实验标记切段，分别给出帧数、命中率、有效率和
最高速度，不需要反复截图或口述终端数据。

详细端口、JSON字段、时间同步、参数范围和异常行为见
[`STREAM_PROTOCOL.md`](STREAM_PROTOCOL.md)。

## 动态滚动录像与逐帧日志

比赛模式保持 `APP_MODE = "stream"`，录像和日志统一由 Windows 接收端
保存，不占用 MaixCAM 本地编码与存储资源：

```powershell
python Vision\windows\stream_receiver.py --duration 60
```

每次实验保存到 Windows 的 `Vision/captures/stream_sessions/`：

```text
stream_YYYYMMDD_HHMMSS/
  video.mp4          # MaixCAM H.264 原码流无损封装
  tracking.csv       # 逐帧检测、滤波、速度与拒绝原因
  stm32_feedback.csv # STM32控制反馈
  video_frames.csv   # 视频帧与遥测的时间匹配
  analysis.txt/json  # 自动统计报告
  session.json       # 设备实际参数和会话状态
```

测试建议 30～60 秒，依次包含静止、慢滚、快滚、换向和短时手部遮挡。
屏幕的红色 `REC` 只表示 Windows 正在采集，不会烧进原始录像。优先通过
调参页或 `iteration_client.py stop` 正常结束，使 MP4 写完索引。

无电脑或网络中断时才使用 `APP_MODE = "record"` 的板端录像兜底；结束后
可临时切到 `"serve"`，从 `http://10.16.6.1:8080/` 下载。

下载后在仓库根目录统计：

```powershell
python Vision\tools\analyze_tracking_log.py <下载目录>\tracking.csv
```

录像与检测来自同一传感器的两个硬件输出通道：识别按相机最高速运行，
识别通道当前为 480×360，录像由底层线程以 448×336、20 FPS 编码。
CSV 的 `elapsed_ms`
从录像启动后开始计时，是日志/录像对齐的权威字段；`video_frame_id`
只是按请求帧率计算的辅助估计。下载后分析工具会调用 `ffprobe` 校验
MP4 的真实帧率、帧数、时长以及与日志的时长差。

`measured hit ratio` 是算法逐帧得到真实测量的比例，`valid output ratio`
还包含短时预测续航；它们不是带人工标注的“识别准确率”。真正判断误检时，
按 `elapsed_ms` 对照原始录像和 CSV。

## STM32 串口协议

STM32 选择题目 2 并按确认键后，通过 USART6 发送：

```text
c2
```

MaixCAM 收到后才以 50 Hz 发送位置误差和轴向速度：

```text
B,error_px,velocity_px_s\n
```

例如钢球位于中心左侧 27 个参考像素、正在以 18 px/s 向视觉右侧运动：

```text
B,-27,18
```

误差和速度均以视觉右侧为正。输出乘以 `CONTROL_OUTPUT_SCALE`，因此无论
检测通道是否降到 480 宽，STM32 看到的仍是原 640 宽标定坐标。长期丢球
发送 `none\n`。题目停止时 STM32 发送 `ok`，MaixCAM 随即停止串口数据帧。
协议实现位于 `maixcam/stm32_link.py` 和 `Core/Src/BallVision.c`，串口为
115200、8N1。

STM32每次平衡电机速度或停止命令后，通过同一 USART6 返回：

```text
F,<seq>,<mcu_ms>,<vision_frame>,<vision_age_ms>,<position_x10>,
  <velocity_x10>,<error_x10>,<p_x100>,<i_x100>,<d_x100>,
  <motor_command>,<motor_status>\n
```

MaixCAM非阻塞解析反馈：`x10` 字段除以 10，`x100` 字段除以 100；
`motor_status` 的 0/1/2/3 分别对应
`HAL_OK/HAL_ERROR/HAL_BUSY/HAL_TIMEOUT`。比赛图传模式将每条反馈转发为
`stm32_feedback` UDP报文，由 Windows同时写入原始 `telemetry.jsonl` 和
专用 `stm32_feedback.csv`；板端 `"record"` 兜底模式也写同名 CSV。
反馈接收、网络转发和日志均不修改 50 Hz `B,...` 输出调度。

## 接线

| MaixCAM | STM32F407 |
|---|---|
| A28 / UART2_TX | PC7 / USART6_RX |
| A29 / UART2_RX | PC6 / USART6_TX |
| GND | GND |

TX/RX 交叉并共地。

管道检测只扫描右端局部区域，并只输出一个右端二维端点。MaixCAM 使用原生色块
扫描，不执行逐帧透视变换、整图掩膜或第二套钢球检测，因此不会给 MaixHub
推理路径增加图像重采样开销。
